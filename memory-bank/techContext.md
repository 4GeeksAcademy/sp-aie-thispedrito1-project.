# Tech Context - HealthCore Digital

## Stack tecnologico
- Frontend principal en Next.js 16 (App Router) con React 19 y TypeScript.
- Estilos con Tailwind CSS v4 via PostCSS.
- Calidad de codigo con ESLint 9 + configuraciones de Next (core web vitals y TypeScript).
- Capa de consumo de datos via fetch HTTP hacia API externa configurada con NEXT_PUBLIC_API_URL.
- Repositorio con estructura multi-area: app web en apps/talent-pipeline-tracker y utilidades/tipos en raiz.
- Backend API en FastAPI con TinyDB para persistencia operativa local de proveedores, usuarios y perfiles.
- Seguridad backend con JWT stateless (python-jose), hash de contrasenas con passlib+bcrypt y dependencia OAuth2PasswordBearer.
- Envio de correo transaccional con Resend (SDK python) para el flujo de restablecimiento de contrasena (AUTH-03); API key y remitente por variables de entorno.
- Cola de tareas asincronas con Celery 5.6 + Redis 7.4 (broker y result backend) y Flower 2.0 para monitorizarla (Ticket #DEV-55). Worker en proceso aparte de FastAPI; `REDIS_URL` por entorno.

## Decisiones de arquitectura tomadas
- Separacion por capas en la app web:
  - UI/rutas en app y components.
  - Integracion API centralizada en services/api.ts.
  - Contratos de datos tipados en types/tracker.ts.
- Estrategia hibrida server/client en Next.js:
  - Rutas App Router para navegacion y estructura.
  - Componentes cliente para interactividad, filtros y estado local.
- Integracion API-first sin backend propio en este modulo:
  - CRUD de candidatos y notas depende de servicio remoto.
- Normalizacion defensiva de payloads:
  - Adaptacion de campos heterogeneos (por ejemplo stage/step, candidate_id/record_id).
  - Manejo explicito de errores 422 para diagnostico rapido.
- Resiliencia de interfaz:
  - Fallback de datos de respaldo en dashboard para no bloquear visualizacion en errores de red.

## Restricciones tecnicas
- Dependencia de API externa: disponibilidad y consistencia de datos condicionadas por servicio remoto.
- Cambios de ruptura en Next.js 16: es obligatorio validar convenciones y APIs vigentes antes de implementar features nuevas.
- Calidad de tipado mejorable: existen usos de any que deben migrarse a unknown + narrowing para robustez.
- Divergencia de modelo de datos entre respuestas de API: requiere mantener mapeadores y validaciones en cliente.
- Alcance actual enfocado en frontend: no hay capa de backend local para control de seguridad avanzada, auditoria o reintentos transaccionales.

El fallback de datos demo del dashboard del tracker se mantiene pero con aviso explicito y boton de reintento.

Los tests de este modulo no tocan Supabase: sobreescriben la dependencia con una SQLite en memoria (StaticPool) por test, mismo principio que la TinyDB temporal de los tests existentes.

El README de un hito puede sugerir una variable dedicada (ej. NEXT_PUBLIC_INVENTORY_API_URL) que no aplica a esta arquitectura real.

- Caching (rama feat/caching-optimisation, 2026-08-10, ver CACHING_REPORT.md para el detalle completo): caché TTL en memoria (`services/api/cache.py`, diccionario con `Lock`, singleton compartido) para GET /inventory/products (30s, TTL corto porque el N+1 de `get_current_stock` contra Supabase costaba ~870ms frio vs ~2-4ms cacheado, medido en vivo) y GET /api/incidents/summary (60s, `IncidentRepository.summary()` barre la tabla 5 veces). Ambas se invalidan explicitamente en los endpoints de escritura correspondientes, nunca dependen solo del TTL. La validacion de stock en `create_consumption` no pasa por cache, asi que el rechazo por stock insuficiente sigue siendo siempre exacto. Gotcha real: la cache es un singleton de proceso, pero `tests/conftest.py` resetea las bases de datos directamente (bypaseando los endpoints que invalidan) — hubo que anadir `cache.clear()` a la fixture `clean_db` autouse o los tests habrian tenido datos "fantasma" entre casos. Frontend: `next/dynamic` solo da code-splitting real quien lo llama desde un Client Component — un Server Component que importa dinamicamente un Client Component NO obtiene code-splitting automatico en Next 16 (confirmado en `node_modules/next/dist/docs/01-app/02-guides/lazy-loading.md`), lo que descarto aplicar la tecnica a la portada del backoffice (`app/page.tsx`, Server Component) y a las secciones estaticas de `uis/website` (ademas alli rompe SEO/SSR sin necesidad). Los dos casos reales aplicados: `ProviderForm` en `/suppliers` (unico formulario que vivia inline en vez de en su propia ruta) y `OrderDetailPanel` en `/inventory/orders` (detalle expandible con IDs de auditoria).
- Docker (2026-08-10, ver seccion dedicada en CLAUDE.md): un contenedor dev con bind mount necesita replicar la misma profundidad relativa que el codigo ya asume en el host — si un modulo importa algo con `../../../algo` o hace `Path(__file__).resolve().parents[N]`, ese `algo` tiene que existir montado en la ruta equivalente dentro del contenedor, no solo la carpeta del propio servicio. `node_modules` necesita su propio volumen anonimo por app cuando se bind-montea la carpeta padre, o el mount tapa los paquetes instalados dentro de la imagen (Linux) con los del host. Turbopack no es fiable dentro de Docker Desktop en Mac (bind mounts via virtiofs le hacen entrar en panico en su grafo de tareas incremental) — usar `--webpack` explicitamente en contenedores, y aun con webpack activar `watchOptions.pollIntervalMs` (Next 16; el viejo env var WATCHPACK_POLLING ya no es el mecanismo documentado) porque los eventos de sistema de archivos tampoco se reenvian de forma fiable. Cambiar de bundler (Turbopack a webpack) sin borrar el `.next` viejo de esa app dejaba una cache en formato incompatible que rompia el hot reload sin ningun error visible en logs.
- Plan de telemetria (rama feat/telemetry-design-plan sobre feat/caching-optimisation, 2026-08-12, ver docs/telemetry/): al disenar el catalogo de eventos contra el CONTEXT del hito se encontraron brechas reales entre el CONTEXT y el codigo vigente de inventario. `VALID_SUPPLY_CATEGORIES` en `services/api/models.py` (`ppe/wound_care/diagnostics/medications/consumables`) sigue sin coincidir con las categorias que pide `CONTEXT-healthcore.es.md` (`medication/ppe/consumable/equipment`) — decision deliberada, ver entrada de instrumentacion abajo: no se migro hoy, es un cambio de modelo de datos mas grande y no bloqueaba el resto.
- Instrumentacion real de telemetria (rama feat/telemetry-capture sobre feat/telemetry-design-plan, 2026-08-14): las tres brechas de esquema que bloqueaban eventos obligatorios se resolvieron con una migracion minima antes de instrumentar. `MedicalSupply` gano `expiry_date: Optional[date]` (nullable — no todo insumo caduca). Tabla nueva `SupplyThreshold` (`supply_id`, `clinic_id`, `minimum_quantity`, unique por par) para el umbral configurable por clinica/producto que el CONTEXT exigia y no existia; fila ausente = "sin umbral configurado", nunca se asume cero. Endpoint nuevo `PATCH /inventory/products/{id}/stock` que siempre responde 400 — le da al principio ya existente del CONTEXT ("el stock nunca se modifica directamente") un punto concreto de aplicacion en vez de un 404 generico, y es lo que dispara `direct_stock_edit_rejected`.
  Hallazgo real durante la implementacion: `get_current_stock` (usado por `/inventory/products`) suma entregas/consumos de TODAS las clinicas para un `supply_id`, no por clinica — un desajuste con como el CONTEXT describe `stock_threshold_triggered` ("el stock ... para esa clinica"). Se agrego `get_current_stock_for_clinic` como funcion separada en vez de tocar el significado de la existente, para no romper silenciosamente la pantalla de productos ni los tests que ya dependen de esa lectura global.
  `stock_threshold_triggered` y `outbound_order_rejected` se emiten en `routes/inventory.py` tras crear la orden (o tras el `InsufficientStockError`). `supply_expiry_flagged` no tiene un disparador de usuario natural (es un job diario en el CONTEXT) — este proyecto no tiene infraestructura de scheduler/cron, asi que se ejecuta una vez en el startup de la API (`main.py::flag_expiring_supplies`) como stand-in suficiente para probar el evento de punta a punta; en produccion real seria un job programado. `login_succeeded`/`login_failed` se emiten desde `routes/auth.py`, no desde el frontend, porque `login_failed` necesita un hash HMAC-SHA256 del email con el secreto de la app (`telemetry_service.hash_identifier`, reutiliza `JWT_SECRET_KEY`) — ese secreto no puede vivir en el navegador. La funcion no distingue `invalid_credentials` de `account_not_found` (aunque el schema lo permite) a proposito: `authenticate_user` ya colapsa ambos casos deliberadamente por anti-enumeracion (mismo principio que `/auth/forgot-password`), y anadir un segundo lookup solo para telemetria reintroduciria esa fuga por timing.
  `inbound_order_created`/`outbound_order_created` se emiten desde el FRONTEND (paginas de `/inventory/orders/{inbound,outbound}`), no desde el backend — reutiliza el mismo patron ya documentado mas abajo de leer `product_category`/`country` de la lista de productos ya cargada, sin peticion extra. `api_latency_recorded` y `api_error_response` reutilizan el `timing_middleware` y el exception handler global ya existentes en `main.py`, sin una segunda medicion.
  `TelemetryService` (`uis/backoffice/services/telemetry.ts`) es deliberadamente el unico modulo del frontend que hace su propio `fetch` fuera de `http.ts`: necesita `NEXT_PUBLIC_TELEMETRY_ENDPOINT` (variable propia, no `NEXT_PUBLIC_API_URL`) y `navigator.sendBeacon`, y sus fallos nunca deben lanzar ni redirigir a login como hace `requestJson`. `track()` es fire-and-forget (no devuelve promesa) a proposito: un fallo de red en telemetria no puede bloquear una accion de negocio real. Reintentos con backoff exponencial (`RETRY_BASE_DELAY_MS * 2^intento`, hasta `MAX_RETRIES`=3, luego se descarta el lote).
  `web_vital_recorded` es un evento nuevo (no estaba en el catalogo original de 23 del plan) anadido a `docs/telemetry/event-schemas.json` (ahora 24) para instrumentar Web Vitals sin emitir un evento fuera de la allowlist gobernada.
- Almacenamiento real de telemetria (rama feat/telemetry-storage sobre main, 2026-08-17): `POST /telemetry/events` reemplaza el stub por persistencia real. Tabla `telemetry_events` (`services/api/telemetry_models.py`) en el mismo Supabase/engine que inventario (`get_inventory_engine`, registrada en `SQLModel.metadata` igual que `inventory_models` — no hace falta variable de entorno nueva ni motor separado). Columna `tags` usa un `TypeDecorator` propio (`_JSONBOrJSON`) que resuelve a `JSONB` en Postgres y a `JSON` generico en la SQLite en memoria de los tests — el proyecto no tiene forma de declarar JSONB puro sin romper esa suite. El indice GIN sobre `tags` usa el kwarg `postgresql_using="gin"` de SQLAlchemy, que otros dialectos simplemente ignoran (SQLite recibe un indice normal en su lugar) en vez de fallar.
  El endpoint acepta el body como `dict` crudo (nunca `list[TelemetryEvent]` tipado) y valida cada evento por separado con `TelemetryEvent.model_validate` dentro de un `try/except` — el modelo `TelemetryEvent` no se modifico. `telemetry_repository.bulk_insert` hace `session.add_all` + un solo `commit` para todo el lote valido.
  Bug real encontrado en la verificacion manual (no en los tests, que usaban timestamps limpios): `TelemetryEvent.timestamp` es un `str` sin validar formato, asi que un valor no parseable como fecha pasa la validacion de Pydantic y solo revienta al construir el registro (`telemetry_service._parse_timestamp` -> `datetime.fromisoformat`). La primera version del endpoint dejaba ese `ValueError` sin capturar y tumbaba el lote completo con un 500 — se envolvio tambien ese paso (no solo la validacion de esquema) en manejo de errores por evento en `routes/telemetry.py`.
  Decision de alcance: los eventos que el backend emite el mismo (via `telemetry_service.emit_backend_event`, sin pasar por este endpoint — `login_failed`, `api_error_response`, `stock_threshold_triggered`, etc.) siguen sin persistirse, solo se loguean como antes. Conectarlos habria significado que `persist_event` abriera una sesion a Supabase desde codigo que corre en cada peticion normal (`routes/auth.py`, el exception handler global, rutas de inventario) usando el engine cacheado de `database.py` directamente — un path que la fixture `client` de los tests (que solo intercepta `Depends(get_inventory_db)`) no cubre, asi que la mayoria de los 80 tests habria intentado conectarse a la Supabase real en cada corrida de `pytest`.
  Gotcha de entorno (Supabase, no del codigo del proyecto): la conexion **directa** (`db.<project-ref>.supabase.co:5432`) solo tiene registro DNS AAAA (IPv6) desde 2024, sin el add-on de IPv4 de pago — en una red sin IPv6 funcional falla con "could not translate host name". La cadena que si funciona es la del **connection pooler** (`aws-0-<region>.pooler.supabase.com:6543`, usuario `postgres.<project-ref>`, no solo `postgres`), que es dual-stack. Vale la pena recordarlo para cualquier proyecto nuevo de Supabase que se conecte por primera vez desde este entorno.

- Auditoria de rendimiento frontend (`feat/frontend-performance-audit`, 2026-09-07). Decisiones tecnicas con evidencia medida, para no repetir el analisis:
  - **styled-jsx dentro de un Client Component no llega en el HTML.** `uis/website/app/application/page.tsx` lo demostraba con un CLS de 0.974: `curl` al HTML de `/application` devolvia 0 coincidencias de `.application-card{`, y la unica hoja enlazada era `globals.css`. Regla general para el proyecto: el CSS critico va en un archivo `.css` importado por la ruta (Next.js lo extrae y lo enlaza en el `<head>`), nunca en `<style jsx>` de un Client Component. Se eligio archivo propio de la ruta en vez de `globals.css` para no enviar estilos del formulario a la portada.
  - **Next.js 16: `priority` de `next/image` esta DEPRECADO** en favor de `preload`, y los docs locales (`node_modules/next/dist/docs/01-app/03-api-reference/02-components/image.md`) recomiendan `loading="eager"` o `fetchPriority="high"` antes que `preload`. Ojo: `next/image` pone `loading="lazy"` por defecto, asi que `fetchPriority="high"` a solas NO basta para el elemento LCP — hace falta tambien `loading="eager"`.
  - **Optimizador integrado de imagenes DESCARTADO a proposito** en `uis/website`: las fotos vienen de `images.unsplash.com`, que ya es un CDN de imagenes (`w=` para redimensionar, `auto=format` para AVIF/WebP). Pasar por `/_next/image` añadia el rodeo navegador -> nuestro servidor -> Unsplash -> nuestro servidor y subio la descarga del LCP de 106 ms a 241 ms, aunque bajara los bytes (139 KB -> 79 KB). - Implementacion del pipeline de negocio con Prefect (`feat/resilient-business-pipeline`, 2026-09-13). Decisiones tecnicas y gotchas reales:
  - **Prefect 3.4.25 en Python 3.9:** es la ultima version compatible con el venv local y no fuerza a cambiar las versiones fijadas de FastAPI/SQLAlchemy/Pydantic (comprobado con `pip install --dry-run --report`). Declarado `prefect>=3.4,<4` en `requirements.txt` y `pyproject.toml`. Sin `PREFECT_API_URL`, un flow arranca la API efimera de Prefect en el propio proceso (~5 s la primera vez), asi que ni el CLI ni la API necesitan servidor ni worker.
  - **El modulo que define un `@flow` no puede usar `from __future__ import annotations` en Python 3.9:** Prefect genera el esquema de parametros con Pydantic y las anotaciones en texto no se resuelven ("CheckParameter is not fully defined"). Solo afecta a `data/pipelines/pipeline.py`.
  - **`retry_condition_fn` en Prefect 3.4 recibe `(task, task_run, state)` y la excepcion va en `state.data`** (comprobado en `prefect/task_engine.py`). Se usa para no reintentar un lock ocupado.
  - **Caché de tasks: `cache_key_fn` basado en el contenido, no en los parametros "de negocio".** La clave de la transformacion hashea los `(id, timestamp)` de los eventos extraidos: `telemetry_events` es append-only, asi que esos ids identifican exactamente los datos. Un evento tardio cambia la clave; un reintento con los mismos datos la reutiliza durante `cache_expiration`. Extraccion y carga llevan `cache_policy=NONE`; si no, la politica por defecto de Prefect 3 intenta hashear sus entradas.
  - **Pandas y datos de `tags` JSON:** construir el DataFrame con `dtype=object` (un entero con algun `None` en la columna se convierte a float) y convertir timestamps con `format="ISO8601"` (`isoformat()` omite microsegundos a cero y Pandas 2 infiere el formato de la primera fila). El segundo lo encontro la ejecucion contra Supabase real, no los tests.
  - **Upsert portable:** `sqlalchemy.dialects.postgresql.insert` y `sqlalchemy.dialects.sqlite.insert` comparten `on_conflict_do_update(index_elements=..., set_=...)`; se elige por `session.get_bind().dialect.name`. Indices parciales con `postgresql_where` y `sqlite_where` a la vez funcionan en ambos motores.
  - **DDL literal en Postgres + metadata en SQLite:** `ensure_reporting_schema` ejecuta `create schema if not exists reporting` y el `create table` exacto del CONTEXT (con `gen_random_uuid()`) solo en Postgres, antes de `create_all`, que al encontrar la tabla ya creada la salta. En SQLite todo sale de la metadata.
  - **Busqueda dentro de JSON/JSONB portable:** `TelemetryEventRecord.tags["eventId"].as_string()` funciona sobre el `TypeDecorator` `_JSONBOrJSON` y compila a `tags ->> 'eventId'` en Postgres (verificado contra Supabase) y a `json_extract` en SQLite.
  - **Tests con Prefect:** `prefect_test_harness` a nivel de modulo, que aisla la base de Prefect y apaga su servidor antes de que pytest cierre la salida (si no, el log de cierre del `atexit` revienta con "I/O operation on closed file"). `TestClient` ejecuta las `BackgroundTasks` antes de devolver la respuesta, lo que permite probar el disparo manual de punta a punta. Cuidado: `database.py` carga `services/api/.env`, asi que en tests `DATABASE_URL` real existe y cualquier codigo que llame a `get_inventory_engine()` sin override hablaria con Supabase. Por eso `pipeline.use_engine(...)` y el monkeypatch de `trigger.launch_manual_run`.
  - **Logging:** con `logging.basicConfig(level=INFO)` en `main.py`, el cliente httpx de Prefect genera una linea por peticion a su API; `httpx` va a WARNING.

Una excepcion dentro de un subflow critico llega al flow padre con su tipo original (`CaptureGapError` sigue identificable en el `except`). - Job nocturno con máquina de estados (`feat/nightly-telemetry-export`, 2026-09-13, Ticket #DEV-53):
  - **Un lock basado en estado necesita una restricción de base de datos, no solo una consulta previa.** "¿Hay alguna fila `processing`?" seguido de un `UPDATE` deja un hueco: dos procesos reales lo atravesaron en el mismo segundo. Un índice único parcial (`unique (job_name) where status = 'processing'`) hace la transición atómica sin añadir columna ni tabla de lock. El que pierde recibe `IntegrityError`, que el repositorio traduce a `ProcessingLockBusy`. Mismo patrón que el lock por mes de `reporting.pipeline_runs`.
  - **Garantía de "nunca queda en processing":** la variable de estado final empieza en `failed`, solo la última línea del `try` la pone en `completed` y el `finally` la escribe con una sesión nueva. Así cubre también `BaseException` (`KeyboardInterrupt`, `SystemExit`). SIGTERM no lanza nada por defecto: hace falta un `signal.signal` que lance una excepción. `subprocess.run` mata al hijo si llega una excepción mientras espera. `kill -9` no se puede capturar; se cubre con rescate por antigüedad al arrancar.
  - **Idempotencia por día con un día abierto:** rechazar `TARGET_DATE >= hoy (UTC)`. Si se exportara un día a medias y se marcara `completed`, la idempotencia impediría para siempre el export completo.
  - **Escritura de archivos de backup:** escribir en `.nombre.tmp` y `os.replace` al final. Si el proceso muere a mitad, no queda un archivo incompleto con el nombre que la siguiente ejecución da por bueno ("solo si no existe").
  - **Contenedores cron:** supercronic en vez del `cron` de Debian, porque cron borra las variables de entorno (`DATABASE_URL` llega por `env_file`) y no escribe en stdout. La descarga se verifica con el sha256 publicado en la API de releases de GitHub (`assets[].digest`), por arquitectura (`TARGETARCH`). Un build con contexto en la raíz del monorepo necesita `<Dockerfile>.dockerignore` junto al Dockerfile.
  - **`docker compose` usa el `.env` de la raíz, no `services/api/.env`**, y `load_dotenv` no sobreescribe variables ya definidas. Si ambos archivos divergen, el contenedor gana. Para probar un contenedor con otra variable sin tocar archivos de secretos: `VAR=... docker compose run --rm --no-deps -e VAR servicio ...`.
  - **Tests de concurrencia con procesos reales:** SQLite en archivo con `connect_args={"timeout": 30}`, arranque sincronizado pasando un instante futuro como argumento, y el DDL hecho antes de lanzarlos (`create(checkfirst=True)` no es atómico).

- Cola de tareas asincronas con Celery (`feat/async-task-queue`, 2026-09-13, Ticket #DEV-55). Lecciones tecnicas reutilizables:
  - **Medir antes de culpar a la cola.** El 202 tardaba ~500 ms y parecia Celery; publicar en Redis costaba 2-4 ms y el tiempo era el lock en Supabase (varios viajes de ~60 ms a Irlanda). Se movio la escritura del lock al worker y la API solo lee.
  - **psycopg2 envia `BEGIN` como viaje aparte.** Para una lectura suelta en una peticion sensible a latencia: `session.connection(execution_options={"isolation_level": "AUTOCOMMIT"})` antes de consultar (~170 -> ~113 ms). Funciona tambien con la SQLite de tests.
  - **Celery `retry_jitter` es `True` por defecto** y sortea la espera entre 0 y el tope: un "backoff" puede reintentar al instante. Desactivarlo si hay que garantizar una espera minima.
  - **`task.apply()` ejecuta los reintentos de autoretry de forma sincrona** (sin esperar el countdown) y llama a `on_failure` al agotarlos: permite probar reintentos + DLQ sin Redis. `on_failure` solo se llama en el fallo definitivo, no en cada reintento.
  - **Un `__call__` propio en una clase base de tarea es seguro:** `push_request` fusiona la peticion existente, asi que `self.request.id` y `retries` se conservan.
  - **El limite duro (`time_limit`) mata el proceso hijo y no llama a `on_failure`**; el blando (`soft_time_limit`) si pasa por el. Poner el blando por debajo si la DLQ depende de `on_failure`.
  - **Con `acks_late`, `visibility_timeout` de Redis debe superar `task_time_limit`**, o Redis reentrega una tarea sana y se ejecuta dos veces.
  - **El logger `celery.app.trace` repite el mensaje crudo de la excepcion** (y su traceback) fuera del control de la tarea: un `logging.Filter` en ese logger que enmascare `msg` y precalcule `record.exc_text`.
  - **Prefect 3 lanza `CancelledRun` cuando un flow devuelve `Cancelled(...)` y se llama directamente**; no devuelve el estado. Hay que capturarlo explicitamente en quien llama (y no dejar que un autoretry lo trate como fallo).
  - **Llamar a Prefect desde un worker de Celery (prefork) funciona** con su API efimera por proceso hijo, igual que en la API. Para simular un fallo de infraestructura sin tocar datos: `PREFECT_API_URL` a un puerto cerrado y `PREFECT_CLIENT_MAX_RETRIES=0`.
